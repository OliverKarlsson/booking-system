# Task Run 1 — Parallel Implementation Plan

Execution plan for building the booking system with parallel sub-agents. Design
rationale lives in [FAQ.md](./FAQ.md); this document is the *contract and work
breakdown*, written so that agents in the same wave never block on each other and never
edit the same file.

**Structure:** 4 waves, 12 tasks. Waves run in sequence; every task within a wave runs
in parallel.

| Wave | Tasks | Parallel | Theme |
|------|-------|----------|-------|
| 1 | T1.1 – T1.3 | 3 | Foundations: shared contract, backend skeleton, frontend shell |
| 2 | T2.1 – T2.4 | 4 | Backend features + rental-unit UI |
| 3 | T3.1 – T3.4 | 4 | Frontend features + OpenAPI + seed |
| 4 | T4.1 | 1 | Integration, end-to-end verification, docs |

## 1. Rules every agent must follow

These are non-negotiable and exist to keep parallel work collision-free.

1. **Stay inside your declared file ownership.** Each task lists *Owns* (create/edit
   freely) and *Reads* (import from, never modify). If you believe you need to edit a
   file another task owns, stop and report it instead — the Wave 4 integration task
   will resolve it.
2. **The contract in §3 is authoritative.** Do not invent field names, status codes, or
   error codes. If something is genuinely unspecified, pick the obvious option, and
   note the choice in your final report.
3. **Wave 1 pre-creates stubs.** Feature agents fill in stub files that already exist
   and are already wired up. Never add route mounts or imports to `app.ts`,
   `router.tsx`, or `db/schema.sql` — they are complete before Wave 2 starts.
4. **The project must compile at the end of your task.** Run `npx tsc --noEmit` in your
   workspace before reporting done.
5. **Write trade-off comments at decision points** — the exclusion constraint, the
   check-versus-constraint split, index choices, pagination. Explain *why*, not *what*.
   No narration of obvious code.
6. **Dates are `YYYY-MM-DD` strings everywhere.** Never construct a JS `Date` from a
   reservation date. See §3.1.
7. **All SQL is parameterised.** No string interpolation into queries, ever — including
   for `ORDER BY` and `LIMIT`. Validate sort/pagination inputs against an allow-list.
8. **Report** at the end: files created, decisions made, anything you couldn't finish.

## 3. The API contract

**All agents code against this.** It is fixed before Wave 1 starts so nobody waits.

### 3.1 Date handling

Reservation dates are **calendar dates**, not instants — Postgres `date` columns,
transmitted as `"YYYY-MM-DD"` strings in JSON.

`date` has no time and no timezone component, so there is no offset for anything to be
shifted by. A stay booked for the 26th is the 26th for every user in every timezone.
Where dates are compared in TypeScript, plain string comparison is correct: for
zero-padded ISO dates, lexicographic order *is* chronological order.

**The `pg` driver must be configured not to coerce `date` into a JS `Date`** — see §4,
"Date handling in the driver". Without that one line the default coercion reintroduces
the exact bug the column type eliminates.

`createdAt` / `updatedAt` are the deliberate exception: those genuinely *are* instants,
so they are `timestamptz` and serialize as ISO 8601 strings.

### 3.2 Entities

```ts
// RentalUnit
{
  id: string;              // uuid v4
  name: string;            // 1–120 chars, required
  timezone: string;        // IANA id, REQUIRED — e.g. 'Europe/Stockholm'.
                           // The authority for "what day is it at this property";
                           // see §3.7. Editable via PATCH.
  address?: {              // all fields optional
    street?: string;
    city?: string;
    postcode?: string;
    country?: string;
  };
  status: 'active' | 'deleted';
  createdAt: string;       // ISO 8601
  updatedAt: string;
}

// Reservation
{
  id: string;              // uuid v4
  rentalUnitId: string;    // uuid v4, must reference an active unit
  guestName: string;       // 1–120 chars, required
  startDate: string;       // 'YYYY-MM-DD', inclusive (check-in)
  endDate: string;         // 'YYYY-MM-DD', EXCLUSIVE (check-out)
  status: 'confirmed' | 'cancelled';
  createdAt: string;
  updatedAt: string;
}
```

**Invariant:** `endDate > startDate` strictly. A reservation is at least one night.

### 3.3 The overlap rule

Interval is half-open `[startDate, endDate)`. Two reservations conflict iff:

```
A.startDate < B.endDate  AND  B.startDate < A.endDate
```

Same-day turnover is **not** a conflict: a reservation ending `2026-03-10` and another
starting `2026-03-10` coexist. Only `status: 'confirmed'` reservations block; cancelled
ones are ignored.

### 3.4 Error envelope

Every non-2xx response:

```json
{
  "error": "Human-readable message",
  "code": "MACHINE_CODE",
  "details": []
}
```

`details` is optional and code-specific.

| Code | HTTP | Meaning |
|------|------|---------|
| `VALIDATION_ERROR` | 400 | Body/query failed Zod validation. `details`: `[{ path, message }]` |
| `NOT_FOUND` | 404 | Resource does not exist (or is soft-deleted) |
| `RENTAL_UNIT_NOT_FOUND` | 404 | Reservation references a nonexistent/deleted unit |
| `BOOKING_CONFLICT` | 409 | Overlaps existing reservation(s). `details`: conflicting reservations (`id`, `guestName`, `startDate`, `endDate`) |
| `UNIT_HAS_RESERVATIONS` | 409 | Cannot delete a unit with non-cancelled reservations |
| `RATE_LIMITED` | 429 | Too many requests |
| `INTERNAL_ERROR` | 500 | Unexpected — never leak internals to the client |

`BOOKING_CONFLICT.details` carrying the conflicting reservation is what lets the UI say
*"conflicts with Jane Doe, 12–15 March"* instead of a generic failure.

### 3.5 List envelope

```json
{
  "data": [ ... ],
  "pagination": { "page": 1, "limit": 20, "total": 57, "totalPages": 3 }
}
```

`page` is 1-based. `limit` defaults to 20, max 100.

### 3.6 Endpoints

#### Rental units

| Method | Path | Notes |
|--------|------|-------|
| `POST` | `/v1/rental-units` | → 201 with the created unit |
| `GET` | `/v1/rental-units` | Query: `page`, `limit`. Excludes soft-deleted |
| `GET` | `/v1/rental-units/:id` | → 200 / 404 (soft-deleted reads as 404) |
| `PATCH` | `/v1/rental-units/:id` | Partial update of `name`, `address` |
| `DELETE` | `/v1/rental-units/:id` | Soft delete → 204 / 404 / 409 |

`DELETE` semantics: sets `status: 'deleted'`. Allowed **only** when the unit has zero
non-cancelled reservations, otherwise 409 `UNIT_HAS_RESERVATIONS`. Must be idempotent —
deleting an already-deleted unit returns 404, same as a nonexistent one.

> Soft delete rather than a hard delete because cancelled reservations may still
> reference the unit; keeping the row keeps those historical references resolvable.

#### Reservations

| Method | Path | Notes |
|--------|------|-------|
| `POST` | `/v1/reservations` | → 201 / 400 / 404 / **409 `BOOKING_CONFLICT`** |
| `GET` | `/v1/reservations` | Filters below |
| `GET` | `/v1/reservations/:id` | → 200 / 404 |
| `PATCH` | `/v1/reservations/:id` | Re-checks overlap, excluding itself |
| `DELETE` | `/v1/reservations/:id` | Cancels (sets `status: 'cancelled'`) → 204 |

`GET /v1/reservations` query params:

- `rentalUnitId` — uuid, filter to one unit
- `from`, `to` — `YYYY-MM-DD`; returns reservations *overlapping* that window (same
  half-open rule as §3.3), not merely contained by it
- `status` — `confirmed` | `cancelled`, defaults to `confirmed`
- `page`, `limit`
- Sorted by `startDate` ascending

#### Dashboard

`GET /v1/dashboard` → 200

**The client sends no date.** See §3.7 — "today" is resolved per unit, in that unit's
own timezone, by the server.

```json
{
  "data": [
    {
      "rentalUnit": { "id": "...", "name": "...", "timezone": "Europe/Stockholm", "address": {} },
      "localDate": "2026-03-26",
      "occupancy": "occupied" | "vacant",
      "currentReservation": { "id": "...", "guestName": "...", "startDate": "...", "endDate": "..." } | null,
      "nextCheckIn": { "id": "...", "guestName": "...", "startDate": "...", "endDate": "..." } | null
    }
  ]
}
```

`localDate` is the date the occupancy was evaluated against, echoed back so the
calculation is inspectable rather than opaque. The UI may display it plainly (*"as of 26
Mar"*), but must not compare it to the viewer's own date — see §3.7.

Semantics, derived directly from the half-open rule, with `D` = that unit's `localDate`:

- **occupied** iff a confirmed reservation has `startDate <= D < endDate`
- A guest checking out *on* `D` → that unit is **vacant** (`endDate == D` fails
  `D < endDate`)
- `nextCheckIn` = earliest confirmed reservation with `startDate > D`. On a back-to-back
  day the departing guest is gone and the arriving guest is the `currentReservation`,
  since they check in on `D` itself
- Soft-deleted units are excluded entirely

`?now=<ISO instant>` is accepted **for tests only**, overriding `now()` so boundary
cases can be driven deterministically. Not part of the client-facing contract.

### 3.7 Timezones and "today"

**All dates are local to the property, always.** A reservation on `2026-03-26` means the
26th *at the flat*. This is the airline-ticket convention — a departure time of 14:30 is
14:30 where the plane leaves from, and nobody converts it.

**Therefore no timezone comparison exists anywhere in this system.** Do not convert
dates for display, do not compare a unit's date against the viewer's, and do not build
UI that reconciles the two. Dates are rendered exactly as stored.

The single exception is a *conversion*, not a comparison: the dashboard's
occupied/vacant badge needs to know what day it currently is at the property. Each unit
carries a required IANA `timezone`, and one SQL expression resolves it per row:

```sql
(now() AT TIME ZONE ru.timezone)::date AS local_date
```

Without it the badge falls back to the server's clock and a Los Angeles flat reads
vacant at 08:00 Stockholm time while the guest is still in it. That is the field's whole
purpose; nothing else in the codebase needs to know a timezone exists.

The field is **editable via `PATCH`** like any other. Because reservation dates are
calendar dates, the timezone never participates in interpreting stored data — changing
it reinterprets nothing and only affects this derived value. Freezing it would protect
nothing while making a mis-picked zone permanently uncorrectable, since units with
reservations also cannot be deleted.

## 4. The overlap guarantee (read before touching T1.2 or T2.2)

**This is the highest-value part of the assignment. Get it exactly right.**

### The rule lives in the schema

Overlap prevention is **not** implemented in application code. It is a database
constraint, and the application's job is only to turn a violation into a good error
message.

```sql
CREATE EXTENSION IF NOT EXISTS btree_gist;

CREATE TABLE rental_units (
  id          uuid PRIMARY KEY,
  name        text NOT NULL CHECK (length(name) BETWEEN 1 AND 120),

  -- IANA identifier ('Europe/Stockholm'), never a fixed offset — the tz database then
  -- handles DST and political timezone changes for us. This is the authority for "what
  -- day is it at this property", which is what occupancy actually depends on.
  --
  -- Validity is enforced in Zod (against Intl.supportedValuesOf('timeZone')), not by a
  -- CHECK constraint: Postgres forbids subqueries in CHECK, so pg_timezone_names can't
  -- be referenced there. Unlike the overlap rule below, this is a plain value-domain
  -- check with no concurrency dimension — nothing is lost by validating it in the
  -- application. A FK to a lookup table synced from pg_timezone_names would be the
  -- stricter option, at the cost of restating the tz database in our schema and having
  -- to refresh it.
  timezone    text NOT NULL,

  street      text,
  city        text,
  postcode    text,
  country     text,
  status      text NOT NULL DEFAULT 'active'
                CHECK (status IN ('active', 'deleted')),
  created_at  timestamptz NOT NULL DEFAULT now(),
  updated_at  timestamptz NOT NULL DEFAULT now()
);

CREATE TABLE reservations (
  id             uuid PRIMARY KEY,
  rental_unit_id uuid NOT NULL REFERENCES rental_units(id),
  guest_name     text NOT NULL CHECK (length(guest_name) BETWEEN 1 AND 120),
  start_date     date NOT NULL,
  end_date       date NOT NULL,
  status         text NOT NULL DEFAULT 'confirmed'
                   CHECK (status IN ('confirmed', 'cancelled')),
  created_at     timestamptz NOT NULL DEFAULT now(),
  updated_at     timestamptz NOT NULL DEFAULT now(),

  CONSTRAINT reservation_valid_range CHECK (end_date > start_date),

  -- THE BOOKING RULE. `[)` is the half-open interval, so a stay ending on the 10th and
  -- one starting on the 10th do not conflict (same-day turnover is allowed). The WHERE
  -- clause is the cancellation exemption. This constraint holds under any concurrency —
  -- there is no lock to take and no isolation level to configure.
  CONSTRAINT reservation_no_overlap EXCLUDE USING gist (
    rental_unit_id WITH =,
    daterange(start_date, end_date, '[)') WITH &&
  ) WHERE (status = 'confirmed')
);

CREATE INDEX reservations_unit_dates_idx
  ON reservations (rental_unit_id, start_date, end_date)
  WHERE status = 'confirmed';
```

`btree_gist` is required because the constraint mixes `=` on a `uuid` with `&&` on a
range; stock GiST operator classes don't cover equality on scalar types. **Creating the
extension is part of T1.2 — nothing works without it.**

### The application layer: good errors, not correctness

A raw constraint violation arrives as SQLSTATE `23P01` with no indication of *which*
booking conflicted, but the UI needs to name the conflicting guest and dates. So the
write path does both, in this order:

```ts
// 1. Query overlapping reservations first — purely to build a useful 409 payload.
//    This SELECT is NOT what makes the operation safe; it races, and that is fine.
const conflicts = await findOverlapping(db, { rentalUnitId, startDate, endDate });
if (conflicts.length) throw new BookingConflictError(conflicts);

// 2. Insert. If a concurrent request slipped in between the SELECT and here, the
//    exclusion constraint rejects this write. Correctness never depended on step 1.
try {
  return await insertReservation(db, reservation);
} catch (err) {
  if (isExclusionViolation(err)) {          // SQLSTATE 23P01
    const raced = await findOverlapping(db, { rentalUnitId, startDate, endDate });
    throw new BookingConflictError(raced);
  }
  throw err;
}
```

**The division of responsibility must be commented in the code:** the check is for
humans, the constraint is for correctness. Deleting the pre-check would degrade error
messages without ever permitting a double booking.

`PATCH` uses the identical path when dates change. No self-exclusion logic is needed —
updating a row does not conflict with its own current values.

### Overlap query

```sql
SELECT * FROM reservations
WHERE rental_unit_id = $1
  AND status = 'confirmed'
  AND daterange(start_date, end_date, '[)') && daterange($2::date, $3::date, '[)')
  AND ($4::uuid IS NULL OR id <> $4)   -- exclude self on PATCH
```

Using `daterange` overlap here rather than hand-written `<`/`>` comparisons keeps one
definition of "overlap" shared with the constraint.

### Date handling in the driver

Configure `pg` so `date` columns come back as **strings**, not JavaScript `Date`
objects — the default coercion reintroduces the exact timezone bug the `date` type
eliminates. This is a one-time setup in T1.2:

```ts
import pg from 'pg';
// 1082 = OID of `date`. Return it verbatim as 'YYYY-MM-DD'; letting node-postgres
// build a Date here would apply the process timezone and can shift the day.
pg.types.setTypeParser(1082, (value: string) => value);
```

### T2.2 — Reservations API + overlap enforcement ⭐

**Owns:** `/backend/src/modules/reservations/**`

**Read §4 in full before writing any code.** This task carries the assignment.

- **The concurrency test** (`reservations.concurrency.test.ts`): fire ~20 simultaneous
  `POST /v1/reservations` for the identical slot on one unit via `Promise.all`, assert
  **exactly one** 201 and the rest 409 `BOOKING_CONFLICT`, then assert the table holds
  exactly one confirmed reservation. A second case proves bookings for *different* units
  all succeed concurrently — the constraint is per-unit, not a global lock.
- **The bypass test:** attempt the overlapping insert in raw SQL, going around the
  service layer entirely, and assert Postgres rejects it with `23P01`. This is what
  demonstrates the guarantee belongs to the database rather than to application code
  that a future change could route around.

### T2.3 — Dashboard API

**Owns:** `/backend/src/modules/dashboard/**`

Implement `GET /v1/dashboard` per §3.6 and §3.7. Compute occupancy, current guest, and
next check-in for every active unit — **each evaluated against its own local date**.

Do this in **one SQL query** — a per-unit loop is an N+1 and exactly the kind of thing
worth avoiding and commenting on. The shape:

```sql
SELECT ru.*, d.local_date, cur.*, nxt.*
FROM rental_units ru
CROSS JOIN LATERAL (
  -- "Today" per property, not per viewer. See §3.7.
  SELECT (COALESCE($1::timestamptz, now()) AT TIME ZONE ru.timezone)::date AS local_date
) d
LEFT JOIN LATERAL (
  SELECT … FROM reservations r
  WHERE r.rental_unit_id = ru.id AND r.status = 'confirmed'
    AND r.start_date <= d.local_date AND r.end_date > d.local_date
  LIMIT 1
) cur ON true
LEFT JOIN LATERAL (
  SELECT … FROM reservations r
  WHERE r.rental_unit_id = ru.id AND r.status = 'confirmed'
    AND r.start_date > d.local_date
  ORDER BY r.start_date LIMIT 1
) nxt ON true
WHERE ru.status = 'active'
ORDER BY ru.name;
```

`$1` is the test-only `?now=` override. Note the partial index from §4 that makes the
laterals fast.

**Tests** covering every boundary from §3.6: guest checking out today (→ vacant), guest
checking in today (→ occupied), back-to-back changeover, unit with no reservations,
unit with only past reservations, unit with only cancelled reservations.

**Plus the timezone test that justifies the whole design:** two units with identical
reservations but different timezones (e.g. `Pacific/Auckland` and `America/Los_Angeles`),
evaluated at a `?now=` instant where their local dates differ — assert they report
*different* occupancy. That is the case a viewer-local implementation gets wrong.
